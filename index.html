AP Join Failures & AAA mostly DOCUMENTED

The common misconception

Default CAPWAP join on a Catalyst 9800 has no AAA/RADIUS step at all. The join sequence is purely certificate/DTLS-based:

Discovery Request/Response → DTLS handshake (cert exchange) → Join Request/Response → image check → Config → Run

Neither the AP join process documentation nor the 9800 join/disconnect troubleshooting guide mentions AAA or RADIUS anywhere in that path. DOCUMENTED

Where AAA actually can enter the picture

  • An optional, off-by-default feature: "Authorize APs against MAC" (AP Policy), which checks the AP's MAC/cert against a local DB or RADIUS before/at join. DOCUMENTED
  • 802.1X AP-as-supplicant — a separate, often-confused mechanism that authenticates the AP's wired port to the switch, not the WLC. DOCUMENTED

Distinguishing AAA-driven vs. CAPWAP/cert-driven in logs

show ap join stats summary
show ap join stats detail
show wireless stats ap discovery
show wireless stats ap join
show logging profile wireless
show dtls connection          (AP-side)

show ap join stats detail gives distinct reason strings per cause — e.g. "Radius authorization of the AP has failed" (AAA-specific) vs. "Certificate payload in join request contains invalid certificate" (cert-specific) vs. image/VLAN/timeout strings. DOCUMENTED

Field takeaway INFERENCE

AAA appears in exactly one narrow, opt-in code path, while cert/license/country/version failures dominate the documented troubleshooting literature. If an AP won't join and AAA/RADIUS wasn't deliberately enabled for AP authorization, chase certificate, licensing, country-code, or version mismatch first — not ISE.

CWA Redirect ACL "Flip Logic" DOCUMENTED

The core mechanism

Cisco's own CWA troubleshooting documentation describes the 9800 redirect ACL as a "punt ACL," not a security ACL:

  • permit = traffic is redirected to the captive portal
  • deny = traffic is exempted from redirection (passes through normally)

This is the inverse of normal ACL semantics (permit=allow, deny=block) — confirmed verbatim by two independent Cisco sources, not inferred.

Correct ACL shape

ip access-list extended REDIRECT
 deny ip any host <ISE-IP>
 deny ip host <ISE-IP> any
 deny udp any any eq domain
 deny udp any eq domain any
 permit tcp any any eq 80

Deny traffic to ISE PSN nodes and DNS; permit (redirect) the rest. Missing the DNS/ISE exemptions causes a redirect loop. DOCUMENTED

The AireOS trap DOCUMENTED

Semantics are inverted again on legacy AireOS controllers: on AireOS, deny means redirect and permit means pass-through — exactly backwards from 9800/IOS-XE. An engineer carrying AireOS habits onto a 9800 (or vice versa) will build the ACL exactly backwards and get a result that looks like "nothing redirects" or "everything redirects," with no obvious error.

FlexConnect caveat DOCUMENTED

For locally-switched APs, the controller automatically swaps all permits and denies when pushing the ACL down to the AP. The AP-local view (show ip access list on the AP CLI) will look inverted relative to the WLC-side definition — this is expected, not corruption.

Most common real-world failure

ACL name mismatch between what ISE sends in the authorization response and what's configured on the WLC. Surfaces in logs as:

SANET_AUTHZ_FAILURE - Redirect ACL Failure
Failed attribute name REDIRECT

ISE's own default ACL name is ACL_WEBAUTH_REDIRECT (underscores) — frequently mistyped with dashes (ACL-WEBAUTH-REDIRECT), creating a silent mismatch. DOCUMENTED

802.11r FT Roaming + CWA Interaction mixed confidence

Is combining FT + CWA on one WLAN supported?

Yes, documented as intentional: Cisco's CWA chapter states CWA "initiates user redirection and authentication at Layer 2, often in combination with MAC filtering or 802.1X authentication." The Local Web Auth chapter has an explicit "Configure WLAN for 802.1X and local web authentication" section. Dot1x-then-webauth is sanctioned design, not a conflated misconfiguration. DOCUMENTED

Open documentation gaps

QuestionStatus
Does the FT PMK cache survive while a client sits in CWA/WEBAUTH_REQUIRED (L2 complete, L3 pending)?Documentation gap — not addressed in either the FT or CWA config guide chapters
Does the session-timeout timer reset on an FT roam, or keep ticking from the original association?Unconfirmed — would explain a delete firing shortly after a successful roam if the answer is "it doesn't reset"
Is "Invalid PMKID" after a roam a mobility/anchor PMK-cache-sync defect rather than an AAA issue?Unconfirmed — a roam that succeeds and is reversed/retried ~1 second later is a classic symptom of two controllers disagreeing on PMK state, but no Cisco source confirms this directly
Does Cisco discourage combining 802.11r with CWA/guest-style portals?No explicit statement found either way — absence of a restriction isn't endorsement

Field recommendation INFERENCE

If you observe a client complete an FT roam successfully, get deleted seconds later with an AUTH_EXPIRED-style reason, retry FT and fail with Invalid PMKID, then recover via full 802.1X — treat the deletion timing (not the PMKID failure) as the thing to escalate to TAC/Bug Search. The PMKID failure is downstream of the deletion, not the trigger.

ISE Deployment & PSN Sizing mostly DOCUMENTED

Other internal Cisco references cover ISE RADIUS/802.1X NAC configuration and ISE deployment/scaling in more depth — check internally before treating this section as the definitive guide. This is a quick-reference summary.

PSN sizing is session-based, not WLC-based

ISE sizing is driven by concurrent active sessions, not endpoint or WLC count. Cisco's tiers:

TierSessionsMax PSNs
Small≤ 50k2-node pair, all personas co-located
Medium≤ 150k6 (PAN+MnT+pxGrid co-located, PSNs dedicated)
Large> 150k50 (PAN, MnT, pxGrid, PSNs all dedicated/separate)

There is no fixed PSN-per-WLC ratio. Redundancy is built per PSN workload group (RADIUS/Guest/CWA, 802.1X, TACACS+) — not per controller. DOCUMENTED

CWA specifically does not support PSN load balancing

Cisco's RADIUS Server Load Balancing documentation states explicitly: CWA does not support load balancing across PSNs. CWA's flow is multi-stage (MAB auth → redirect → second RADIUS auth → CoA), and all of it must correlate against session state on the same PSN. A load balancer can split the second-stage auth or CoA to a different node than the one holding the original session, breaking the flow intermittently. The "least outstanding" load-balancing method is specifically called out as unsuitable for CWA/NAC scenarios.

Documented alternative: a WLC-driven ordered RADIUS server list (with dead-server detection/deadtime tuned), not an external load balancer — unless that LB specifically guarantees session affinity across the whole CWA flow. DOCUMENTED

Hardware and placement gotchas

  • ISE appliance hardware cannot be upgraded post-purchase (no added RAM/CPU/disk) — undersizing at purchase is permanent. DOCUMENTED
  • SNS-3895 is PAN/MnT-only — using it as a PSN provides "no additional value" per Cisco, a common oversizing mistake. DOCUMENTED
  • Large deployments require PAN pairs on identical hardware, with MnT hardware ≥ PAN. Only 2 MnT nodes are supported total — no horizontal MnT scaling. DOCUMENTED
  • PAN auto-failover needs 3+ nodes; a health-check node per site if PANs split across data centers. DOCUMENTED
  • Mismatched ISE software versions between PAN and a joining node blocks registration — a common upgrade-sequencing mistake. DOCUMENTED
  • Geo-distribute PSNs close to the NAS devices (WLCs/APs) they serve; <5ms inter-node latency target. PSN-to-WLC proximity specifically (vs. inter-ISE-node) is inference extrapolated from the general proximity principle.

9800-side pairing gotchas

  • 9800 mobility MAC defaults to chassis base MAC; in HA SSO pairs it must be set manually or it changes on failover, silently breaking mobility tunnels. DOCUMENTED
  • N+1 ≠ HA SSO: SSO is a same-chassis-pair stateful pair; N+1 is AP site-tag-based failover to a separate standby controller — different mechanisms, often conflated. DOCUMENTED
  • Catalyst Center hard rule: manual CLI changes on a Catalyst-Center-managed 9800 get silently overwritten on the next provisioning sync — all changes must go through templates/profiles. DOCUMENTED

Intermittent / "Random" Failure Checklist mostly DOCUMENTED

For symptoms that look random, affect different users unpredictably, and are hard to reproduce on demand — check these in order.

1. RADIUS/AAA health (WLC side)

  • RADIUS-driven client exclusion when the server returns a VLAN/ACL name that doesn't exist locally ("VLAN mismatch," "ACL mismatch")
  • EAP timeout from dot1x timeout / dot1x request retries windows — often client/driver-side, not server-side
  • Use RadioActive Tracing (debug wireless mac <addr> monitor-time <N>) to elevate a specific MAC to debug level across every process

DOCUMENTED

2. ISE-side signals

  • Node out of sync with the Primary Admin node (replication lag) — cascades to delayed Application Server init (normally 15-35 min)
  • Certificate issues surface distinctly: self-signed/untrusted ISE certs show as "Alert (Level: Fatal, Description: Certificate Unknown)" in captures
  • Check per-node CPU/latency/memory/disk for overload before assuming a logic bug

DOCUMENTED

3. Infrastructure signals mistaken for "wireless"

  • DHCP Required mismatch across foreign/anchor controllers → stale IP retained across a roam → DHCP NAK
  • Internal 9800 DHCP defaults to an infinite lease — can silently exhaust the pool over time
  • VLAN/trunk or FlexConnect native-VLAN misconfig — explains behavior that's site-inconsistent (works at some APs/buildings, not others)
  • Stale device-tracking entries causing false "IP theft" exclusions

DOCUMENTED

4. Standard correlation method

Controller:  RadioActive trace by client MAC + exact timestamp
AP:          AP-side client debug (bundle collector, Flex log level)
ISE:         Live Logs for the same MAC/timestamp
Optional:    simultaneous EPC on WLC + TCPDump on ISE PSN interface

TAC's first ask is always: exact reproduction timestamp, client MAC/IP/username/session ID, and a support bundle/RA trace captured live — continued logging overwrites debug buffers, so this can't be reconstructed after the fact. DOCUMENTED

Pattern From a Real Case (anonymized)

No customer name, case number, or network specifics appear here — this is the generalized technical pattern only. The full case-specific writeup lives in a separate, private, access-controlled repository.

Observed pattern

  1. Client completes an 802.11r FT roam successfully, reaches RUN state.
  2. ~3 seconds later, controller deletes the client with an AUTH_EXPIRED-family reason — despite the client having been fully associated.
  3. ~1 second after that, client retries FT and fails with Invalid PMKID (downstream of the deletion, not the cause).
  4. Client recovers via a fresh full 802.1X association.
  5. Client later stalls in CWA/WEBAUTH_REQUIRED and times out.

Why this is interesting

Cisco's own DevNet reference defines the AUTH_EXPIRED-family delete reason as a pre-association timeout ("client did auth phase, but never completed association"). That doesn't match a client that had already reached RUN. This contradiction — not the downstream PMKID failure — is the right thing to escalate to TAC/Bug Search. See the FT Roaming + CWA Interaction topic for the open questions this raises.
