How confidence is marked

Three statuses appear throughout this guide, next to every claim that isn't plain fact:

Documented — confirmed directly from a cited Cisco source: a config guide, a TAC troubleshooting doc, a DevNet reference, or Cisco Press.

Inference — a reasonable extrapolation from documented principles, not a verbatim Cisco statement.

Unconfirmed — a plausible hypothesis that couldn't be verified in this pass. Needs TAC, Bug Search, or further digging before you rely on it.

What this intentionally leaves out

This guide stays scoped to Cisco-platform implementation — not RF/802.11 theory. Channels, modulation, MIMO, spectrum analysis, and roaming fundamentals are CWNP's domain (CWNA/CWDP/CWNE), and this guide defers to it rather than duplicating it. It's also not a customer case tracker: the one case pattern included here has every identifying detail stripped out.

What this does and doesn't tell you

  • Download/upload — real throughput to a nearby Cloudflare edge node, over HTTPS, from this browser tab. It reflects the whole path: Wi-Fi link, LAN, router, and the ISP uplink — not Wi-Fi in isolation. A slow result here doesn't by itself tell you which hop is the bottleneck.
  • Idle latency/jitter — round-trip time and its variance to that same edge node, measured with the link otherwise quiet. High jitter with otherwise fine throughput is a classic sign of airtime contention or a congested channel, worth cross-checking against the QoS & voice/video section.
  • Loaded latency (bufferbloat) — the same latency measurement, taken again while the download and upload tests are actively saturating the link. The gap between idle and loaded latency is a real, well-known diagnostic: a large jump means something in the path (often a consumer router's own buffer, sometimes the AP itself) is queuing packets under load rather than dropping or prioritizing them. This matters directly for voice/video and gaming, which degrade from added latency long before raw throughput becomes the problem.
  • Connection detail (RTT, retransmits, packets lost) — these come from Cloudflare's own edge, reported back for the specific TCP connection this test used, via a Server-Timing response header their network stack sets. This is the server's measurement of that one connection, not a browser estimate layered on top — but it's one connection's data, not a long-run average, so treat a single bad reading as a prompt to re-run the test rather than a confirmed diagnosis.
  • Not measured, and not measurable from any browser on any OS: RSSI, SNR, channel, channel width, PHY mode (802.11n/ac/ax/be), MCS index, spatial streams, or negotiated Tx rate. Browsers deliberately have no API for this — it's an OS/driver privacy boundary, not a limitation of this page specifically. This page does not estimate or infer any of those values from throughput, latency, or any other number above — too many non-Wi-Fi factors (server distance, TCP window scaling, ISP congestion) affect those same numbers for a correlation to mean anything.

documented — a true crash file is a separate, specific artifact, not the general tech-support bundle above:

2.4 GHz — channels 1–14

documented — frequency (MHz) = 2407 + 5 × channel for channels 1–13; channel 14 is a fixed special case at 2484 MHz (Japan-only, 802.11b only, not legal for 802.11g/n). Only channels 1, 6, and 11 are non-overlapping at 20 MHz width in the US — every other channel overlaps at least one neighbor's spectrum, which is why "channel 1/6/11 only" remains the standard field recommendation for 2.4 GHz deployments.

documented — frequency (MHz) = 5950 + 5 × channel for 6 GHz (channels 1–233, odd-numbered in the standard 20 MHz plan). The tradeoff is Standard Power's AFC (Automated Frequency Coordination) requirement: an AP must query an FCC-approved AFC system for a clear channel/power allocation before transmitting above LPI limits — this is new infrastructure most engineers haven't dealt with on prior Wi-Fi generations.

Wi-Fi 7's headline 46 Gbps figure is a theoretical ceiling at maximum spatial streams/channel width/MCS — no currently shipping AP hardware approaches it; real-world Wi-Fi 7 AP throughput is bounded by actual radio chain count (typically 2x2 or 4x4 on current Catalyst/Meraki hardware), not the amendment's theoretical maximum.

MU-MIMO vs. OFDMA — the distinction that actually matters operationally

inference — these are frequently conflated but solve different problems. MU-MIMO (introduced 11ac, improved in 11ax) lets the AP talk to multiple clients simultaneously using spatial separation — most valuable with few, high-throughput clients. OFDMA (new in 11ax/Wi-Fi 6) subdivides a channel into resource units so many clients can each get a small efficient slice at once — most valuable in high-density, many-small-packet environments (IoT, dense classrooms/stadiums). A dense-client-count problem is an OFDMA story; a few-clients-need-max-throughput problem is a MU-MIMO story — picking the wrong lever to tune for a given symptom wastes field time.

AP join failures & AAA

Catalyst 9800 (IOS-XE) · mostly documented

The misconception to rule out first

Default CAPWAP join on a 9800 has no AAA/RADIUS step at all. The sequence is purely certificate/DTLS-based:

Discovery → DTLS handshake (cert exchange) → Join → image check → Config → Run

Where AAA actually enters the picture

  • An optional, off by default feature — "Authorize APs against MAC" — checks the AP's MAC/cert against a local DB or RADIUS before join.
  • 802.1X AP-as-supplicant: a separate, often-confused mechanism that authenticates the AP's wired port to the switch, not the WLC.

AP crash & reboot loops

Catalyst 9800 (IOS-XE) · mostly documented

Stuck pre-join: a corrupted-image boot loop

documented — Field Notice FN74109 (CSCvx32806, plus CSCwc72021/CSCwd90081) documents Wave 2 11ac APs (2800/3800/4800/1560/IW6330/ESW6300) and Catalyst 9100 Wi-Fi 6/6E APs downloading a corrupted image over CAPWAP from a 9800 controller, then boot-looping on it. Exact console signature:

verify signature failed for /bootpart/part1/ramfs_data_cisco.cpio.lzma
Image signature verification failure: -3

On the uplink switch, the affected AP shows as generic "Ieee PD" rather than its model name in show power inline. Fixed in 8.10.185.0, 17.3.7, 17.6.6, 17.9.3, and 17.11.1+. APs with the alt-boot enhancement self-recover after 5 failed attempts by falling back to their backup partition; older u-boot versions need console-level ubi remove/ubi create recovery.

Joins fine, then reboots/rejoins repeatedly afterward

documented — work this from the WLC side first, not the AP console:

show ap crash                                              ! AP crash files stored on the WLC
dir all | i crash
show wireless stats ap history mac-address <mac>           ! last reboot type/reason
show wireless stats ap mac <radio-mac> join detailed        ! disconnect type/reason/count

Cisco's own diagnostic logic: look for APs with abnormally low "Assoc Uptime" relative to overall uptime (a sign of repeated reload), then check whether the affected APs share a switch, a wncd process, or a recent config change:

Mass AP disconnects

Catalyst 9800 (IOS-XE) · mostly documented

Same switch or stack

documented — Cisco's documented correlation step for simultaneous AP drops is explicitly to check "if those APs were in same switch." A shared uplink, a switch reload, a spanning-tree event, or total PoE power-budget exhaustion on that one switch (see the PoE & AP power section — ILPOWER_POWER_DENY) all produce this exact signature.

Scattered across different, unrelated switches

documented — this points at the controller side, specifically per-process load, not the access layer. Cisco's own troubleshooting flow checks wncd (the per-AP-group wireless control process) utilization: "disconnections could be due to high wncd CPU utilization and WLC not been able to process packets received from APs."

show wireless loadbalance ap affinity wncd <0-7>   ! which APs share a wncd instance
sh proc cpu platform | i wncd                       ! per-process CPU

If every affected AP maps to the same wncd instance, that instance — not the network — is the shared cause.

Roaming: Fast Transition (802.11r), 802.11k, 802.11v

Catalyst 9800 (IOS-XE 17.12) · mostly documented

802.11r Fast Transition — what it actually does

FT lets a client pre-negotiate keys with a target AP before it roams: "enables the initial handshake with a new AP even before the corresponding client roams to the target access point," letting client and AP "do the Pairwise Transient Key (PTK) calculation in advance." Keys are applied "after the client responds to the reassociation request." The WLAN config carries this as its own AKM type — Fast Transition (FT) — separate from the WPA2/802.1X AKMs.

Over-the-Air vs. Over-the-DS

  • Over-the-Air: "The client communicates directly with the target AP using IEEE 802.11 authentication with the FT authentication algorithm."
  • Over-the-DS: "The client communicates with the target AP through the current AP" — FT action frames are relayed via the current AP/controller.
  • FT-SAE uses a new AKM OUI (00-0F-AC:9); the STA includes a Mobility Domain Element (MDE) and RSNE in the (re)association request, the AP echoes FTE/MDE/RSNE back, and the two sides run a Fast Transition 4-way handshake after SAE auth. A mismatched MDE returns STATUS_INVALID_MDE; an AKM mismatch returns STATUS_INVALID_AKMP.

Mobility Domain ID (MDID) — the roaming boundary FT actually uses

"The MDID is used by 802.11r to define the network boundary where fast roaming is supported." Inside one domain, "APs share PMKs," letting clients "roam quickly without fully reauthenticating." Two ways to form a domain: static MDID assignment, or dynamic site-tag-based grouping. If an MDID is configured, it overrides the site tag for PMK sharing control — a frequent source of "FT works on some APs but not others" when a subset of APs got an explicit MDID and the rest didn't.

MDID has no CLI/GUI path — "you can configure MDID only through the open configuration model" (RESTCONF/NETCONF/YANG). Scale: up to 100 APs and 1,000 PMK cache entries per AP per domain (17.2.1). It does not function for Flex APs in standalone mode, since controller coordination is required.

Configuration (CLI)

wlan <profile-name>
 shutdown
 security ft
 security wpa akm ft dot1x        ! or: ft psk | ft sae
 no shutdown

Disabling specific behavior: no security ft {adaptive | over-the-ds | reassociation-timeout <sec>}. FT-over-DS is enabled by default on WLAN creation — a WLAN can be "FT-capable" without anyone deliberately turning on the DS path.

Restrictions — the real failure modes, quoted directly

  • "EAP LEAP method is not supported."
  • "Traffic Specification (TSPEC) is not supported for 802.11r fast roaming. Therefore, RIC IE handling is not supported."
  • "Legacy clients cannot associate with a WLAN that has 802.11r enabled if the driver of the supplicant…is old and not aware of the additional AKM suites in the IE." Workaround: run two SSIDs with the same name but different security settings (FT vs. non-FT) — or clients that are 802.11r-capable can still associate as plain 802.11i if both AKM types are enabled on the WLAN.
  • "To avoid any Denial of Service (DoS) attack, each Cisco WLC allows a maximum of three Fast Transition handshakes with different APs."
  • "FT-SAE Over-the-DS roam is not supported in FlexConnect local authentication mode." Cisco's general recommendation is Over-the-Air FT for FlexConnect deployments.
  • "In Cisco Wave 2 APs, local switching local authentication with 802.11r is not supported."
  • FlexConnect local-auth FT specifically: supports Over-the-Air roaming only (no Over-the-DS); supports adaptive 11r for Apple clients; supports both FT+802.1X and FT+PSK; up to 100 APs per PMK-sharing group by default (300 in high-scale mode), 1,000 PMK entries/AP. Pre-17.2.1, local-auth FlexConnect clients couldn't use FT at all — only centrally authenticated clients could.

OKC — the non-11r fast-roam alternative, for context

Opportunistic Key Caching caches one PMK per client across APs sharing a WLAN, "even when roaming between multiple APs," and "works with WPA2-EAP as a fast roaming technique." Client support splits by vendor: "Microsoft and some Android clients support OKC," while "Apple and few Android clients support 802.11r." OKC is on by default per WLAN (okc / no okc under the WLAN); disabling it disables it even for clients that could use it. If a mixed-client SSID shows some clients fast-roaming and others doing full reauth, this split is the first thing to check — not a controller defect.

802.11k — Assisted Roaming (neighbor reports)

documented — "Assisted Roaming" on the 9800 is really two features. First, genuine 802.11k: the controller "allows an AP to inform 802.11k-capable clients of neighboring BSSIDs (APs in the same SSID)" so the client doesn't have to blind-scan every channel to find a roam target. Second, a Cisco-proprietary addition for clients that don't speak 802.11k: a prediction neighbor list built from each client's probe-RSSI history, which the controller then uses to actively deny association to a sub-optimal AP (up to a configurable denial count) if the client ignores the predicted list.

  • Restriction: "This feature is supported only on 802.11n capable indoor access points."
  • Single-band WLANs advertise up to 6 neighbors; dual-band up to 12.
  • "You can configure assisted roaming only using the CLI" — beyond the WLAN-level enable checkboxes, there's no GUI path for the prediction/denial tuning parameters.
  • Avoid two SSIDs sharing the exact same name — Cisco calls this out as a cause of roaming issues independent of 11k.

802.11k configuration (CLI)

! Global:
wireless assisted-roaming floor-bias <5-25 dBm>        ! default 15
wireless assisted-roaming prediction-minimum <count>   ! default 3
wireless assisted-roaming denial-maximum <1-10>        ! default 5

! Per-WLAN:
wlan <wlan-id>
 assisted-roaming neighbor-list     ! 11k neighbor list — ON by default at WLAN creation
 assisted-roaming dual-list         ! dual-band list — ON by default
 assisted-roaming prediction        ! prediction-list denial feature — OFF by default

Turning on assisted-roaming prediction on a WLAN that already has load balancing enabled silently disables load balancing on that WLAN (Cisco documents a warning being shown, but it's easy to miss in a scripted push). If client distribution across APs changes right after someone enables assisted-roaming prediction, this is the first thing to check.

Verification: show wlan id <wlan-id> shows the neighbor-list/dual-list/prediction state per WLAN.

802.11v — BSS Transition Management

documented — 802.11v covers two different benefits that are easy to conflate: network-assisted power savings (Directed Multicast Service, BSS Max Idle Period) and network-assisted roaming (BSS Transition Management, "BTM"). BTM covers three triggers: a client-initiated query before it roams on its own; an AP-initiated request "when an AP is heavily loaded"; and an AP-initiated request "when a client's RSSI and rate do not meet the requirements."

The request is advisory unless you force it. Cisco states plainly that a BTM request "is a suggestion (or advice) given to a client, which the client can choose to follow or ignore" — unless disassociation-imminent is enabled, which turns it into a forced transition. A client "ignoring" a steering attempt is often this setting, not a client-side bug.

802.11v configuration (CLI)

wlan <profile-name>
 shutdown
 bss-transition
 bss-transition disassociation-imminent   ! optional — forces the transition
 no shutdown

GUI equivalents (Configuration > Tags & Profiles > WLANs > Advanced): BSS Transition (the base enable), Dual Neighbor List (includes neighbors from the AP's other radio slot — 2.4/5 GHz — in the BTM response), BSS Max Idle Service / BSS Max Idle Protected (power-save idle timer; "Protected" requires authenticated frames to reset the counter), and Directed Multicast Service (converts a multicast stream to unicast for any DMS-capable client).

802.11v prerequisites and restrictions

  • "Client needs to support 802.11v BSS Transition" — there's no fallback behavior for clients that don't; a BTM request to a non-supporting client is simply ignored.
  • Explicitly called out for "Apple clients like Apple iPad, iPhone…that run on Apple iOS version 7 or later."
  • "Supports local mode; also supports FlexConnect access points in central authentication modes only" — BTM on a FlexConnect AP doing local authentication is not supported.

gap — no dedicated show/verification command for BSS Transition Management state appears in the 9800 17.12 config guide chapter itself; the only confirmed check is reading the WLAN's configured BTM settings back via show wlan name <profile> / show run wlan, by analogy with how OKC and assisted-roaming settings are verified elsewhere in the same guide. Treat that command as a reasonable inference, not a cited one-to-one for this specific feature.

Field recommendation inference

If a client completes an FT roam, gets deleted seconds later with an AUTH_EXPIRED-style reason, retries FT and fails with Invalid PMKID, then recovers via full 802.1X — escalate the deletion timing, not the PMKID failure. The PMKID failure is downstream, not the trigger. (This pattern was originally observed on a WLAN with no CWA involved; if you hit it on a CWA WLAN, see the Identity Services Engine section for the open questions specific to that overlap.)

Hardware & placement gotchas

  • ISE appliance hardware can't be upgraded after purchase — undersizing at buy time is permanent.
  • SNS-3895 is PAN/MnT-only; using it as a PSN gives "no additional value" per Cisco.
  • Only 2 MnT nodes are supported total — no horizontal MnT scaling.
  • PAN auto-failover needs 3+ nodes; a health-check node per site if PANs split across data centers.
  • Mismatched ISE versions between PAN and a joining node blocks registration outright.

9800-side pairing gotchas

  • Mobility MAC defaults to chassis base MAC; in HA SSO pairs, set it manually or it changes on failover and silently breaks mobility tunnels.
  • N+1 is not HA SSO — SSO is a same-chassis stateful pair, N+1 is AP site-tag failover to a separate standby. Different mechanisms, often conflated.
  • On a Catalyst-Center-managed 9800, manual CLI changes get silently overwritten on the next provisioning sync.

Central Web Authentication (CWA)

Redirect ACL logic — the core mechanism

Cisco's own CWA troubleshooting docs call the 9800 redirect ACL a punt ACL, not a security ACL:

  • permit — traffic is redirected to the portal
  • deny — traffic is exempted from redirection, passes through normally

That's the inverse of normal ACL semantics, confirmed verbatim by two independent Cisco sources.

Correct ACL shape

ip access-list extended REDIRECT
 deny ip any host <ISE-IP>
 deny ip host <ISE-IP> any
 deny udp any any eq domain
 deny udp any eq domain any
 permit tcp any any eq 80

Deny traffic to ISE PSNs and DNS; permit the rest to redirect. Skip the DNS/ISE exemptions and you get a redirect loop.

The AireOS trap

Semantics flip again on legacy AireOS: there, deny means redirect and permit means pass-through — exactly backwards from 9800. An engineer carrying habits from one platform to the other will build the ACL exactly backwards, with no obvious error on screen.

FlexConnect caveat

For locally-switched APs, the controller swaps every permit/deny when pushing the ACL to the AP. The AP-local view (show ip access list) looks inverted relative to the WLC side — expected, not corruption.

Most common real failure

ACL name mismatch between what ISE sends and what's configured on the WLC. Surfaces as:

SANET_AUTHZ_FAILURE - Redirect ACL Failure
Failed attribute name REDIRECT

ISE's default ACL name is ACL_WEBAUTH_REDIRECT (underscores) — frequently retyped with dashes, which breaks the match silently.

Verifying the redirect

show wireless client mac-address <mac> detail   (ACL under "Server Policies")
show ip access list                               (AP CLI, FlexConnect only)
debug wireless mac <mac> monitor-time <sec>

unconfirmed — show ip access-lists (plural, WLC-side) with hit counters for this specific flow is a standard IOS-XE command that almost certainly works, but no CWA-specific doc spells out this exact use.

CWA doesn't support PSN load balancing

CWA's flow is multi-stage: MAB auth → redirect → second RADIUS auth → CoA, and all of it must land on the same PSN. A load balancer that splits the second-stage auth or CoA to a different node breaks the flow intermittently — exactly the shape of a "random" failure that's hard to reproduce on demand. Cisco's own "least outstanding" method is called out as unsuitable here.

Documented alternative: a WLC-driven ordered RADIUS server list with dead-server detection tuned, not an external load balancer, unless it specifically guarantees affinity across the whole CWA flow.

Is combining 802.11r FT with CWA on one WLAN supported?

documented as intentional. Cisco's CWA chapter says CWA "initiates user redirection and authentication at Layer 2, often in combination with MAC filtering or 802.1X authentication." Dot1x-then-webauth is sanctioned design, not an accidental overlap.

Meraki cloud-managed (MR)

mostly documented

The architecture inverts the usual model

Meraki is event-driven RPC: the cloud initiates calls to devices for config push and telemetry — the opposite of a WLC pulling AP state. User traffic never touches the cloud; it goes direct to LAN/WAN. There's no CAPWAP and no controller to tunnel to — APs are independently intelligent.

Documented: on cloud connectivity loss, "the Meraki hardware device will continue to run with its last known configuration until cloud connectivity is restored." inference: SSIDs keep broadcasting and clients keep associating locally during an outage — only dashboard-dependent functions (new config, Live Tools, Sign-on-splash auth, see below) are affected.

Guest / web auth splash types

  • Click-through — acknowledgment only, no credentials.
  • Sign-on — via Meraki auth, RADIUS, LDAP, AD, or Google/Entra. With Sign-on + RADIUS, the client's credentials route through the Meraki Cloud Controller, which issues the Access-Request to the external server (e.g. ISE) — the cloud is in the auth path, not the local AP.

802.1X / MAB with ISE

Shared secret must match on the SSID config and the RADIUS server. Enabling "Cisco ISE Authentication" lets Meraki honor ISE's url-redirect AVPair for CWA and auto-enables CoA.

CoA/Disconnect port is platform-specific — a frequent source of "RADIUS works but CoA doesn't": the AP's UDP port must be reachable from the RADIUS server at 1700 for ISE, 3799 for other NAC vendors. CoA behavior itself changed between firmware MR25 and MR26 (full disassociation vs. in-session EAP reauth). Cloud RADIUS proxy does not support CoA at all.

The RADIUS test tool has a specific blind spot

Dashboard's built-in RADIUS test triggers an EAP-PEAP/MS-CHAPv2 exchange to confirm reachability and credentials. It fails for EAP-TLS every time, because the test has no client certificate to present — that failure means nothing about whether real EAP-TLS clients will work. Test those with an actual device.

Live Tools — and the one that doesn't exist on MR

Monitor > Access Points > Tools: Ping (to client or AP), ARP table, Traceroute, Dashboard throughput test (AP↔dashboard only, not internet), blink LEDs, reboot, splash page test.

No internet access — AP itself vs. a specific client

documented — check which side is actually failing before troubleshooting. The AP converts itself to repeater mode if it "cannot receive an ARP reply packet from the default gateway on the LAN," or "cannot obtain a valid IP address via DHCP" — in either case it broadcasts a <SSID>-bad-gateway or <SSID>-scanning SSID as the signal, which is an AP-side symptom, not a client-side one. Diagnose with a laptop/Wireshark on the same switch port.

For a client that associates fine but has no internet: Meraki's own resolution guide starts with "verify that the gateway is correct and reachable" — ping the gateway from both the client and the AP (Wireless > Access point > Tools). DNS is called out separately as "one of the most common causes of client connection problems" — switching the client to a public resolver (8.8.8.8) is Meraki's own suggested isolation step. If that doesn't clear it, check Network-wide > Client for a firewall rule or group policy applied to that client or subnet.

DHCP failures — Bridge mode vs. NAT mode

documented — in Bridge mode, "wireless and wired clients connected to Meraki APs receive an IP address from the DHCP server on the wired LAN" — the AP does no DHCP of its own. Check pool exhaustion first (a sudden client surge is the most commonly cited trigger); then ping the DHCP server from Wireless > Access point > Tools — no response means "a connection issue exists somewhere upstream from the AP," not a Wi-Fi problem. If the DHCP server sits on a different broadcast domain, confirm an IP helper / DHCP relay agent is configured — Meraki documents a missing relay as a direct cause of the no_offers_received condition. Last check: an SSID VLAN tag colliding with the upstream trunk's native VLAN, since "the upstream port drops packets tagged with its native VLAN."

In NAT mode, DHCP is handled entirely by the AP, so the bridge-mode causes (pool/relay/VLAN) don't apply. Capture on the client with Wireshark to confirm an ACK actually comes back — "the DHCP process will not complete without an ACK message" — and check the event log (Network Wide > Monitor > Client) for the exact step that failed. If a PSK or RADIUS credential is involved, re-verify it in a private browser window first; a previously-saved key can be stale in a browser's autofill cache.

Mixed Meraki + Catalyst 9800 fleets

This is onboarding/monitoring only, not native MR-equivalent management. Documented gotchas are all 9800-side: onboarding needs privilege-15 credentials with correct AAA (aaa authentication login default local / aaa authorization exec default local), and conflicts can come from VTY line limits, HTTP/NETCONF ACL conflicts, SSH port/rotary conflicts, or unsupported SSH encryption algorithms.

Outdoor & mesh

documented

RAP, MAP, and the backhaul protocol

RAPs have a wired link to the controller. MAPs connect wirelessly, shipping with radio role = MAP by default (config ap role {rootAP|meshAP} to change it). MAPs find the best wireless path back to a RAP using Cisco's Adaptive Wireless Path Protocol (AWPP), forming a tree with keepalive adjacency request/response messages; VLAN-tagged traffic tunnels over that backhaul link.

The join sequence has an extra step

On a 9800, Ethernet-connected MAPs get MAC-authorized during a normal CAPWAP join — same as any indoor AP. A wirelessly-joining MAP is only authorized once it secures an AWPP link to its parent. The backhaul link has to exist before controller authorization completes, which indoor wired-join APs never have to do.

Bridge Group Name — the most common connectivity cause

Default BGN from manufacturing is NULL, which lets a MAP join before an admin assigns a network-specific BGN (max 10 characters). BGNs segment mesh networks sharing a channel. A MAP with a mismatched BGN scans 10 times for its correct parent; after 10 failed scans, it joins a non-matching BGN parent for 15 minutes before retrying its own. Cisco's documented fix order: reconfigure the farthest node first, then work back toward the RAP — reconfiguring in the wrong order can strand nodes mid-change.

Why hop count matters more than it sounds like it should

Hop count isn't just added latency — it's a throughput multiplier against the whole backhaul. A client two hops out getting 5 Mbps can be consuming 40 Mbps of total backhaul capacity to deliver it. CAPWAP encapsulation itself costs up to 15% throughput on top of that.

Backhaul interference indoor troubleshooting doesn't prepare you for

  • Weather radar occupies 5600–5650 MHz (channels 124/128) and triggers DFS "quiet"/"silent" mode — a mesh link that drops specifically on those channels isn't a config problem.
  • Collocated mesh nodes need physical separation — 10 ft vertical or 100 ft horizontal — to avoid self-interference between the node's own radios.

Backhaul up with decent SNR, but link rate/throughput is still bad

documented — confirm antenna gain configuration matches the installed hardware before touching anything RF-related. Cisco states the antenna gain for a mesh AP "must be configured to match that of the antenna installed" (entered in 0.5 dBm units) — this is a required configuration step, not an optional tuning knob, and a mismatch here is invisible in a basic SNR check. Also confirm backhaul band: the mesh backhaul on these platforms defaults to, and is locked to, 802.11a — "You cannot change the backhaul interface to 802.11b/g" — so any plan assuming 2.4 GHz backhaul capacity starts from a wrong premise. Cisco's own recommendation is to leave the backhaul rate set to Auto rather than a fixed rate, which is exactly the setting that self-corrects a rate mismatch like this.

If this is specifically two collocated/closely-mounted mesh nodes: the 10 ft vertical / 100 ft horizontal spacing requirement above exists precisely to avoid the nodes' own radios interfering with each other. Nodes mounted closer than that will show self-interference that looks exactly like a generic weak/unstable backhaul, and no channel or power change will fix it.

HA SSO & N+1 failover

Catalyst 9800 · mostly documented, with real gaps noted

RMI and RP — the link that has to be right

The Redundancy Management Interface (RMI) and Redundancy Port (RP) must sit on the same subnet, isolated from every other interface on the box. Cisco's documented addressing recommendation is a 169.254.x.x/16 block derived from the management interface — explicitly not 10.10.10.x/24. RP round-trip time must stay under 80ms, and the HA port maps only to a 1Gbps interface (SFP takes priority over RJ-45 if both are present).

Split-brain is a named, documented condition

If RP goes down and RMI becomes unreachable at the same time, Cisco calls this a double fault: "Both controllers may become active, causing a network conflict." Role negotiation only resumes once connectivity is restored, and the controller that came up last stays active — not the one that was active before the fault. If RP alone drops during HA sync, the standby intentionally crashes when IPC communication fails, rather than risk running split.

If RP is down but RMI/gateway is still reachable: the standby becomes active, and the previous active enters rp-rec-mode (visible in the hostname) with every interface admin-down except the wireless management interface on the RMI IP.

What a clean SSO actually preserves

Only one CAPWAP tunnel is maintained between APs and the active controller at a time — "zero downtime for client services and no SSID outages" is the documented target, and database mirroring prevents APs from re-entering discovery.

What does not survive a switchover, documented explicitly: clients not yet in RUN state are removed, and purged entirely after 300 seconds if they haven't reconnected; NBAR flow state in local mode is lost; AVC flow context must be relearned; voice calls can't be recognized post-switchover because RTP/RTCP-based policy breaks; TCP sessions must re-establish; statistics tables aren't synchronized at all.

N+1 — a terminology gap, now resolved with sourced nuance

documented — the mechanism most engineers mean by "N+1" (AP failover to a separate standby controller, not a chassis pair) maps to Cisco's documented AP priming profile system: primary/secondary/tertiary controller statements pushed to APs via priming-override, mapped by name-regex filter or directly by AP MAC address. Confirmed directly against the 9800 config guide: the term "N+1" there primarily names the N+1 Hitless Rolling AP Upgrade feature — "a controller-assisted method that migrates APs to a temporary controller during upgrade, avoiding service disruption" — not chassis HA SSO.

The same chapter does use "N+1" once in a looser, redundancy-architecture sense, under "Best practices for N+1 redundancy deployments": "Use spare controllers in N+1 redundancy deployments to allow APs to fail over when the primary controller becomes non-operational. This approach ensures minimal network downtime, typically lasting 30 to 40 seconds, as APs discover and join the network in local mode." That's the spare-controller failover idea engineers mean — but Cisco never equates it with AP priming terminology in any reachable document. Treat "N+1" on the 9800 as the rolling-upgrade/spare-controller term, and AP priming as the separate, actual failover mechanism — related in effect, not the same documented concept.

Documented failover logic: an AP always returns to its primary once that controller is available again. Tertiary is only used if both primary and secondary are down, and if secondary recovers while primary is still down, the AP stays on tertiary — there's no mid-outage fallback to secondary.

show wireless profile ap priming summary

That last command is the one that actually answers "why didn't this AP fail over as expected" — it shows whether the AP received the priming configuration at all.

Root causes Cisco documents

  • Active and standby must run the same mode (Install or Bundle) and the same image version. Auto-upgrade exists specifically to handle "one of the redundancy port is upgraded to a newer version, and the other one is not upgraded at the same time."
  • Mismatched wireless trustpoints — same name, different keys — prevent the trustpoint from coming up after SSO forms.
  • Don't enable hyper-threading on HA VMs: "HA keepalives are lost, and a stack merge may occur."
  • VM snapshots of HA hosts are unsupported and can crash the controller.

802.1X supplicant-side failures

strong sourcing on the core thesis

The single error code that hides four different causes

Cisco's own "Cheat Sheet for Common Wireless Issues" documents AAA Error "-4" (Authentication Failed) as the WLC's single, most common error — and its documented cause list includes mismatched EAP methods between client and server, an expired client certificate, and an expired server certificate, all collapsed into the same error code. This is the concrete, Cisco-documented proof that a basic "auth failed" symptom cannot by itself distinguish a client problem from a server problem. Don't let that one error code drive an escalation decision on its own.

Machine vs. user auth ordering (EAP chaining / TEAP)

In a chained TEAP session, user identity is attempted first (ISE log 11573 Selected identity type 'User'), then machine (11574 Selected identity type 'Machine'). If user auth fails but machine auth succeeds, ISE still completes the session: 11566 TEAP inner method finished with failure for the user attempt, followed by 33517 Sent TEAP Intermediate Result TLV indicating failure, then a successful machine attempt (12528 Inner EAP-TLS authentication succeeded), and the overall session can still return 11002 Returned RADIUS Access-Accept.

Authorization is then driven by the Network Access.EapChainingResult attribute — Cisco's own documentation describes policy rules written explicitly around "machine authenticated but user not" versus "both now authenticated," confirming this differential treatment is intentional, documented design, not an edge case.

Client-side certificate trust

The WLC-side signature for a client that never responds is unambiguous: DOT1X-5-FAIL with reason (Timeout), repeated Retrying (count 3) method dot1x, ending in CO_CLIENT_DELETE_REASON_CONNECT_TIMEOUT. Cisco's own remediation text for this exact scenario reads: "Ensure wireless client trust RADIUS' certificate" — stated as a client-side action item, not a server fix.

ISE's own error 5440 corroborates from the other side: "the endpoint supplicant does not complete the EAP authentication within the configured timeout," logged as "ISE sending 'Access-Challenge' but ISE didn't receive any response." ISE did its job; the client went silent. The same abandonment pattern — "Endpoint <MAC> abandoned EAP session <session-id> and started EAP session" — recurs as a named, numbered event across independent Cisco troubleshooting documents, not an ad hoc string.

unconfirmed — no Cisco documentation found states the exact log text for "untrusted root CA," "certificate expired," or "clock skew" as distinct, separately-coded failure reasons. These are well-established real-world causes, but any specific wording attributed to them should be treated as inference, not a cited string, until confirmed against a live ISE instance or TAC case.

Multicast & broadcast over WLAN

mostly documented

IGMP snooping doesn't stop at the controller

The controller still forwards multicast to every AP over CAPWAP — snooping suppresses flooding at the AP-to-client, over-the-air hop, not the controller-to-AP hop. Only APs with an actively subscribed client send the multicast stream on a given WLAN. The controller builds unique MGIDs from the (L3 group, VLAN) pair and tracks per-AP client membership against them.

IGMPv1/MLDv1 snooping is fully supported; IGMPv2/v3 support is explicitly documented as "limited" — if the upstream switch doesn't recognize IGMPv3, hosts simply don't get traffic.

DTIM interval — a documented, hard recommendation

documented — Cisco states this without qualification: "The only recommended DTIM values are 1 and 2; higher DTIM values will likely cause communications problems." The AP buffers broadcast/multicast frames and only releases them at the DTIM beacon — a 100ms beacon period with DTIM=1 delivers multicast 10 times per second; raising DTIM delays delivery proportionally.

inference — raising DTIM on APs serving battery-saving handhelds, badge scanners, or IoT devices delays multicast/broadcast delivery in exact proportion to beacon-interval × DTIM value. This is commonly misdiagnosed as a flaky application ("my paging app is slow," "discovery is unreliable") rather than traced back to the RF profile's DTIM setting.

The only confirmed CAC-related text found is "SIP CAC is not supported" for centrally-switched traffic, plus an undocumented CLI fragment (ap dot11 {24|5|6}ghz cac voice acm) with no accompanying bandwidth percentage, rejection statistics, or show commands. The untrusted uplink problem, in two distinct forms

Catalyst 9000 switchports default to trusted, but two separate documented failure modes still happen in the field:

  • Wired-side remarking — an intermediate switch remarks DSCP 46 down to CS1, degrading WMM all the way to Background before the traffic ever reaches the AP.
  • Outer-header-only remarking — a switch on the AP's own uplink can only see the outer CAPWAP header, not the tunneled client traffic inside it. The inner client DSCP survives untouched, so the client-side marking looks perfectly fine — but the AP-to-WLC transport itself is deprioritized at every hop, producing jitter and loss that a client-side-only inspection will never explain.

Cisco's documented 5-step verification: capture at the source, check every intermediate switch config, capture before and after each switch plus at the WLC and the destination, simulate the path, then cross-check against the 9800 best-practice document. Current trust-boundary commands on 9000-series: trust device <type>, auto qos trust {cos|dscp}, auto qos voip {cisco-phone|cisco-softphone|trust}, verified via show auto qos and show policy-map interface. An untrusted/mismatched peer causes both CoS and DSCP to reset to 0.

inference — no single Cisco flowchart unifies "choppy voice/video" troubleshooting. 9800 ISSU upgrade methodology

documented, with explicit internal inconsistencies noted

ISSU requires a real HA pair — there's no standalone fallback

ISSU "upgrades the controller software image to a later release while the network continues to forward packets," on 9800-80/40/L/CL/M/H1/H2, install mode only. Cisco's own prerequisite check in show issu state detail validates "Standby Online" and "SSO Mode" before allowing activation. There is no documented standalone ISSU workflow anywhere in the config guide — the state machine depends on a standby to absorb traffic, so a standalone 9800 has nothing to activate first.

gap — Cisco does not document what happens if install activate issu is attempted on a standalone controller. It may fail the prerequisite check cleanly, or it may not — this is unconfirmed. For non-HA controllers, Cisco instead documents "N+1 Hitless Rolling AP Upgrade" (a separate controller pair, APs move site-tag by site-tag) as the hitless alternative. That is not ISSU and shouldn't be conflated with it.

The process flow and what to monitor

Image syncs to standby → AP predownload (no service impact) → standby reloads to the new version first while the active continues serving on the old version, forming a temporary mixed-version SSO pair → switchover (the upgraded unit becomes active) → former active reloads to match → staggered AP rejoin cycle → install commit.

show issu state detail      ! primary monitor; shows state transitions and abort-timer countdown
show redundancy              ! Active/Standby roles, "Communications = Up", peer "STANDBY HOT"
show install summary         ! I/U/C/D package flags, abort-timer status
show chassis rmi
show ap image                ! AP predownload tracking

Minor documentation inconsistency worth knowing: show redundancy appears in the separate upgrade and troubleshooting guides but not in the core ISSU config-guide chapter itself.

Rollback — default timer and real triggers

Default auto-abort timer: 360 minutes (6 hours), configurable 30–1200 via install activate issu auto-abort-timer <min>. If install commit isn't issued before expiry, the device reloads back to the previous version automatically.

install commit                      ! persist the upgrade
install abort issu                   ! manual rollback — pre-commit only
install auto-abort-timer stop        ! disables the timer; still requires a manual commit later

Documented rollback triggers: TFTP/image download failure, checksum mismatch, activating before AP predownload completes, auto-abort timer expiry, and config incompatibility causing MCL/PRC sync failures — Cisco cites specific real examples: the domain command removed in 17.6.x, snmp-server enable traps hsrp removed in 17.4.x, and invalid WPA3 AKM configuration.

Cisco's own tech note tells engineers to avoid ISSU entirely on specific builds — known defects CSCws19380 and CSCws35670 cause instability specifically in 17.15.1–17.15.4d and 17.18.1–17.18.2, and Cisco recommends a standard upgrade instead of ISSU on those exact releases. This is worth stating directly: the "safe" path is not universally safe, and Cisco documents that itself.

Confirming a supported path before you start

ISSU is supported EM-to-EM within the same train, not more than three years apart, and within any release of the same EM. Not supported: cross-major-train moves (16.x→17.x, 17.x→18.x), SM-to-EM or EM-to-SM moves, special/engineering images, LDPE↔NPE moves, downgrades, and a hard break at 27.1.1 with no ISSU path into it from any prior release. There is no live show issu capability command — Cisco publishes a static compatibility matrix instead, which has to be checked as a lookup, not queried from the CLI. show issu state detail's system check only validates runtime readiness, not version-pair eligibility — passing that check does not mean the version pair is actually supported.

AP-side behavior — even "successful" ISSU involves a rejoin

APs stay joined through most of the process, and predownload itself has no service impact — but after cutover, APs move in staggered sub-groups via ap upgrade staggered, and Cisco's documentation states directly: "when the APs rejoin, they rejoin with V2." That's a real reload and CAPWAP rejoin per AP sub-group, staggered to limit blast radius — not a seamless failover with zero rejoin, even on a fully successful run.

Cisco's own documentation is internally inconsistent on one point: one section says a mid-process SSO/HA event stops the rolling AP upgrade and requires a manual resume; another section says switchover auto-resumes it. This isn't resolved here — treat it as a known documentation gap rather than picking a side. Known defect CSCws53690 (fixed in 17.18.3) caused unwanted AP disjoin specifically during ISSU from 17.12.6a to 17.18.2, confirming AP disjoin is a real documented failure mode even on an otherwise-supported upgrade path.

Layer 2 switching for AP uplinks

mixed confidence — see panels. Scope: Layer 2 only, no routing/L3

This is the section to bounce back to whenever a client-side or AAA investigation stalls, and the real cause turns out to be sitting one layer down. Everything here is Layer 2 switching only — trunk/access ports, 802.1Q tagging, native VLAN. No routing protocols, no SVIs, no inter-VLAN routing. An AP that never joins the WLC is extremely often an untagged-VLAN or trunk/access mismatch, not an AAA/RADIUS problem — misdiagnosing which layer the fault lives on wastes more field time than almost anything else in this guide.

Trunk vs. access port — what's actually documented for AP uplinks

documented for FlexConnect specifically: Cisco's 9800 FlexConnect chapter shows the AP uplink on a trunk port, explicitly for wired-VLAN separation of locally-switched WLANs: switchport mode trunk, switchport trunk native vlan 100, switchport trunk allowed vlan 101, with the AP needing "IP connectivity on the native VLAN."

inference — for standard local-mode/central-switching deployments, Cisco never states outright "configure the AP switchport as access mode." That's near-universal field practice, consistent with how CAPWAP actually works: in local/central-switching mode, client VLAN tagging happens inside the CAPWAP tunnel at the WLC, not via 802.1Q on the AP's physical wire — so the AP's own uplink only needs a single VLAN (access mode) to reach the controller. FlexConnect is the one mode Cisco's own docs show genuinely needing a trunk, because that's the mode where VLANs are switched locally at the AP instead of tunneled to the WLC.

802.1Q native VLAN — the documented mismatch symptom isn't what most engineers expect

documented — Cisco's Catalyst 9300 VLAN Trunks guide is explicit: "the device forwards untagged traffic in the native VLAN configured for the port," and "make sure the native VLAN for an IEEE 802.1Q trunk is the same on both ends of the trunk link." The documented symptom of a mismatch is a spanning-tree loop — "if the native VLAN on one end of the trunk is different from the native VLAN on the other end, spanning-tree loops might result" — not primarily a clean error message.

CDP does have a documented mismatch-detection role: an "enhanced reporting mechanism" flags "mismatched native VLAN IDs (IEEE 802.1Q) on connected ports," with messages sendable "to the console or to a logging server." unverified — the specific, widely field-quoted syslog string %CDP-4-NATIVE_VLAN_MISMATCH could not be confirmed on any live Cisco.com page despite real search effort. Treat that exact mnemonic as commonly-seen-in-the-field, not vendor-confirmed, until you see it on your own switch.

Why the untagged VLAN matters for AP join specifically

When no client VLAN is explicitly configured for a policy profile, Cisco documents that "the AP native VLAN is used" — so an AP sitting on the wrong native/untagged VLAN doesn't throw a clean "wrong VLAN" error. It silently loses IP reachability to the controller, and the symptom shows up as a stuck or endlessly-retrying CAPWAP discovery, which is easy to misroute to an AAA/RADIUS investigation that was never going to find anything. Rule out the native VLAN before escalating a join failure as an authentication problem.

Mobility groups — still the live mechanism on IOS-XE, not an AireOS holdover

documented — a mobility group "defines a set of controllers identified by the same mobility group name" and "enables seamless roaming and state and context sharing for wireless clients." Members "dynamically share information and forward data traffic when inter-controller or inter-subnet roaming occurs," and they "share the context and state of client devices and their list of access points," which "prevents controllers from identifying access points from other controllers as rogue devices." Discovery/peering is explicit, not automatic: "each controller is configured with a list of the other mobility group members." On a client join, "the controller sends a unicast message, or a multicast message if mobility multicast is configured, to all controllers in the mobility group."

The documented symptom of a mismatched mobility group

documented — the group-name requirement is explicitly tied to fast Layer 2 roaming: controllers must share the same mobility group name "when a fast layer2 roam like Fast Transition (FT) or Cisco Centralized Key Management (CCKM) is in use." inference — this is the direct mechanical explanation for the classic field symptom "client roams to a different controller and does a full 802.1X instead of a fast roam": a mobility group name mismatch (or a controller sitting outside the group entirely) forces the roam down to full re-authentication because the FT/CCKM key material can't be validated against a peer the controller doesn't recognize as a trusted group member.

show wireless stats mobility tracks this as a named, counted condition — a "Group mismatch" field appears under both "Handoff Status Received" and "Handoff Status Sent." A nonzero counter there is hard evidence, not a guess.

Separately documented, not a mobility-group issue: "client roaming is not supported if there is a WLAN profile mismatch" between controllers — a different root cause with the same symptom (roam fails or falls back to full auth), so don't assume group name is the only thing to check.

Anchor vs. foreign — current 9800 terms and CLI

documented definitions: "Anchor controller: the original controller where the client is first authenticated and where session anchoring remains, maintaining the primary client database entry." "Foreign controller: the new controller to which the client connects after roaming, which receives a copy of the client database entry marked as a foreign entry." For guest deployments this is the controller pair most engineers mean by "auto-anchor mobility" — Cisco's current 9800 docs describe the mechanism this way without using that exact phrase as a feature name; the GUI/CLI feature name is Export Anchor.

Role split, quoted directly from the Cisco TAC configuration doc: "Foreign controller: This WLC owns layer 2 or the wireless side… All client traffic for the anchored WLANs is encapsulated into the mobility tunnel to be sent to the anchor." "Anchor controller: This is the layer 3 exit point… decapsulates or terminates the client traffic into the exit point (VLAN)."

A hard matching requirement, stated directly: "it is mandatory that WLAN and Policy Profile names and configurations match on both foreign 9800 WLC and anchor 9800 WLC with the exception of VLAN under the Policy Profile." The VLAN itself is intentionally allowed to differ — that's the whole point of anchoring guest traffic to a DMZ VLAN that doesn't exist on the foreign controller.

  • "You must not configure mobility peers and export anchor at the same time. That is an invalid configuration scenario."
  • "You must not use the Export Anchor setting, for any policy profile tied to a WLAN profile on a controller with access points." (The anchor controller is a Layer-3 exit point, not an AP-serving controller for that WLAN.)

The mobility tunnel — CAPWAP on IOS-XE, not EoIP

documented, directly confirmed — "the Cisco Catalyst 9800 Series Wireless Controller mobility tunnel is a CAPWAP tunnel with a control path (UDP 16666) and a data path (UDP 16667)." The control path "uses DTLS encryption by default," supported DTLS version 1.2. Data-path encryption (data-link-encryption / data-DTLS) is optional and must be matched on both ends — "If the configurations do not match, the system disables the mobility data path."

documented, platform distinction confirmed by direct comparison rather than assumed: EoIP (Ethernet over IP) is an AireOS-era term, not a current IOS-XE/9800 term. The AireOS 8.5 configuration guide uses it directly, describing the encrypted mobility tunnel as using "UDP port 16667, instead of EoIP, to send the data traffic" — i.e. on AireOS, EoIP is the default unencrypted data-path encapsulation that the encrypted tunnel replaces. The 9800 mobility-tunnel documentation never mentions EoIP at all; its data path is CAPWAP/UDP 16667 unconditionally, encrypted or not.

inference — in a mixed AireOS+9800 (IRCM) deployment, "control plane encryption is always enabled" regardless of platform, and if you enable data encryption on the 9800 side you must also enable it on the AireOS side with config mobility group member data-dtls enable — a mismatch here, not a missing EoIP tunnel, is the documented failure mode on mixed deployments.

Mobility tunnels have two platform-specific restrictions worth knowing before troubleshooting a cert error: "Mobility tunnels do not support ECDSA-based certificates or ECDSA-based trustpoints," and 9800-CL peers using self-signed certs need an additional SSC hash validation step.

FlexConnect — local vs. central switching

documented definitions, current 9800 FlexConnect chapter: Locally switched — "the AP forwards client data directly to the local LAN or VLAN at the site instead of tunneling it through the controller." Centrally switched — "the AP forwards the client's data traffic to the controller, depending on the WLAN configuration."

FlexConnect exists specifically for "branch office and remote office deployments," letting branch APs be managed "through a wide area network (WAN) link without deploying a controller in each office." Documented WAN requirements: round-trip latency "must not exceed 300 milliseconds (ms) between the access point and the controller," and FlexConnect "supports up to 4 fragmented packets or a 576-byte MTU WAN link." Local authentication specifically is called out as useful when you "cannot maintain a remote office setup of a minimum bandwidth of 128 kbps with the round-trip latency no greater than 100 ms."

Standalone mode — what happens when the WAN/controller link drops

documented, exact trigger: "Whenever a FlexConnect AP disassociates from controller, it moves to the standalone mode." Effect: "Centrally switched clients are disassociated. However, the FlexConnect access point continues to serve locally switched clients." This is the single most important FlexConnect fact for sizing a design — a branch WLAN that must survive a WAN outage has to be locally switched; a centrally-switched WLAN at a branch site is defined to drop its clients the moment the WAN link does.

Security-type behavior in standalone mode is also explicit: open/shared/WPA-PSK/WPA2-PSK WLANs "enter the local authentication, local switching state and continue new client authentications" with no controller needed. 802.1X/WPA-802.1X/WPA2-802.1X/CCKM WLANs "require an external or local RADIUS server to remain operational" — i.e. 802.1X branch clients only keep working in standalone mode if local EAP/RADIUS is configured on the AP itself, not by default.

documented recovery sequence, quoted directly — this is the exact, field-relevant timeline for "AP stuck in standalone": "The AP attempts to discover for five times and if it still cannot find the controller, it tries to renew the DHCP on the ethernet interface to get a new DHCP IP." "The AP will retry for five times, and if that fails, the AP will renew the IP address of the interface again, this will happen for three attempts." "If the three attempts fail, the AP will fall back to the static IP and will reboot (only if the AP is configured with a static IP)." Reboot rationale given directly: "Reboot is done to remove the possibility of any unknown error the AP configuration." On reconnecting: "the AP disassociates clients, applies new configuration, and resumes normal connectivity."

Also documented: a controller normally doesn't use a backup RADIUS server for 802.1X — "A controller does not use a backup RADIUS server. The controller uses the backup RADIUS server in local authentication mode." That only applies once the AP is already in local/standalone authentication, not in normal connected operation.

On the 9800, FlexConnect ACLs attach via a Flex Profile, not centrally like a redirect ACL on the WLC. VLAN mapping and ACL assignment live in the same place:

9800/IOS-XE does not use the AireOS term "FlexConnect Group" — the current grouping/config-distribution mechanism is the site tag, which "allows you to efficiently manage AP profiles and flex profiles associated with specific network sites."

A branch AP that was never explicitly moved onto a real site tag will show exactly that symptom — roams that work on paper but keep failing or re-authenticating in the field. Capacity note: "You can have a maximum of 100 access points for each flex connect site."

Split tunneling and DNS during web authentication

During web-auth on a locally-switched FlexConnect WLAN, DNS has a documented, deliberately centralized exception: "client DNS replies must pass through the controller during authentication" — specifically, "the FlexConnect APs allows only DNS and DHCP messages; the APs forward the DNS reply messages to the controller before web-authentication… is complete." Only after web-auth completes does traffic switch fully locally: "all traffic switches locally." A branch guest/webauth SSID that seems to redirect correctly but then can't resolve anything post-login, or vice versa, is a sign this handoff point is misconfigured rather than a generic DNS problem.

Split tunneling itself is configured as an ACL path: define the ACL, attach it as an ACL policy under the flex profile, map a split MAC ACL name within the wireless policy profile, then apply the site/policy tags — the same ACL-via-flex-profile mechanism used for general FlexConnect ACLs above, not a separate feature.

documented operational caveat, easy to trigger by accident during a "quick fix": "When you apply a configuration change to a locally switched WLAN, the access point resets the radio, causing associated client devices to disassociate… Modify the configuration only during a maintenance window." A VLAN-mapping tweak pushed mid-day to fix one client will knock every other client on that AP's radio off at the same moment.

AireOS & Mobility Express

documented

The CLI isn't just "older" — it's a different shape

AireOS is flat and non-modal: commands fully qualify their target in one line (config wlan create, config wlan interface), with no config-mode sub-shell to step into. There's also no running/startup split — config lives as XML in RAM and only reaches NVRAM via an explicit save config; logging out or resetting prompts you to save first. 9800/IOS-XE uses the modal config-mode convention most engineers already expect.

The config model itself is restructured, not just renamed

AireOS binds a WLAN directly to a VLAN interface, with AP Groups remapping that WLAN-to-VLAN binding per site. The 9800 decouples the same idea into five pieces: WLAN Profile (SSID/L2 security) + Policy Profile (VLAN/ACL/QoS) + Policy Tag (binds the two) + RF Tag + Site Tag + AP Join Profile. Changing any tag forces an AP rejoin — a side effect that surprises engineers used to AireOS's more direct model.

Debugging works completely differently

AireOS9800 / IOS-XE

On AireOS, starting a new debug session kills any other active one — a second engineer debugging a different client on the same box will silently stop your trace. There's no equivalent collision on the 9800's condition-based model.

Mobility Express is not the same thing as the 9800's EWC

Classic Mobility Express is AireOS running on an AP acting as its own controller — no separate WLC hardware. Scale depends on which AP holds the Primary role: 1540/1815/1830/1850 top out at 50 APs/1000 clients; 1560/2800/3800/4800 reach 100 APs/2000 clients; the hard ceiling across the line is 100 APs/2000 clients. No Cisco table extends this to Wi-Fi 6 APs under classic ME.

Confirm you're looking at an ME deployment, not a true WLC, with show version on the AP — it reports AP Image Type: MOBILITY EXPRESS IMAGE when it's acting as its own controller.

Don't confuse this with the Catalyst 9800 Embedded Wireless Controller (EWC) — a separate, IOS-XE-based product, not AireOS ME. EWC itself is now end-of-sale (11/29/2024) with support ending 11/30/2029 and no replacement product. If you're inheriting an EWC deployment, there's no "upgrade path" to plan for — only a platform change.

Primary AP election and failover

Election priority, in order: a pinned "User Defined Master" > "Next Preferred Master" > highest-capability hardware > lowest client load > lowest MAC address. Mechanism is VRRP under the hood. No consolidated ME-vs-full-WLC feature parity table exists on Cisco.com — that gap is confirmed, not just unresearched; don't assume one platform's feature set carries over to the other without checking the specific feature.

Web GUI won't load / management access blocked

documented — check HTTP vs. HTTPS state before anything else. A browser request to http:// on a controller that's never had webmode enabled simply won't load — try https:// before assuming the management interface itself is unreachable. If instead you're trying to reach the GUI over a wireless client associated to that same controller/AP: Management via Wireless is disabled by default, and even when enabled it only "blocks wireless management access to the same controller that the wireless client device is currently associated with" — it does nothing to stop a wireless client associated to a different controller from reaching this one. Mobility groups — the legacy AireOS model

legacy terminology — AireOS's "mobility group" concept predates the 9800/IOS-XE mobility architecture and is kept here deliberately, since current IOS-XE deployment guidance is covered separately in the Mobility & FlexConnect section. On AireOS, a mobility group is a named set of controllers sharing client/AP context so clients roam seamlessly across them; group membership is a manually maintained peer list, not auto-discovered. The classic unencrypted inter-controller data tunnel on AireOS uses EoIP (Ethernet over IP) — Cisco's own 8.5 configuration guide describes the encrypted alternative as using "UDP port 16667, instead of EoIP, to send the data traffic," i.e. EoIP is the AireOS-era default that the encrypted tunnel replaces. This EoIP terminology does not carry over to IOS-XE/9800, which uses CAPWAP (UDP 16666 control / 16667 data) unconditionally for its mobility tunnel — see the Mobility & FlexConnect section for the current platform's architecture.

Field case pattern

anonymized

No customer name, case number, or network specifics appear here — this is the generalized technical pattern only. The case-specific writeup lives in a separate, private, access-controlled repository.

Observed pattern

  1. Client completes an 802.11r FT roam successfully, reaches RUN state.
  2. About three seconds later, the controller deletes the client with an AUTH_EXPIRED-family reason — despite the client having been fully associated.
  3. About one second after that, the client retries FT and fails with Invalid PMKID — downstream of the deletion, not the cause.
  4. Client recovers via a fresh full 802.1X association.
  5. Client later stalls in CWA / WEBAUTH_REQUIRED and times out.

Why this is worth escalating

Cisco's own DevNet reference defines the AUTH_EXPIRED-family delete reason as a pre-association timeout — "client did auth phase, but never completed association." That doesn't match a client that had already reached RUN. This contradiction, not the downstream PMKID failure, is what belongs in front of TAC or Bug Search. See Identity Services Engine for the open questions it raises.
