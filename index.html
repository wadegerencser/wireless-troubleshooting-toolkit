How confidence is marked

Three statuses appear throughout this guide, next to every claim that isn't plain fact:

Documented — confirmed directly from a cited Cisco source: a config guide, a TAC troubleshooting doc, a DevNet reference, or Cisco Press.

Inference — a reasonable extrapolation from documented principles, not a verbatim Cisco statement.

Unconfirmed — a plausible hypothesis that couldn't be verified in this pass. Needs TAC, Bug Search, or further digging before you rely on it.

What this intentionally leaves out

This guide stays scoped to Cisco-platform implementation — not RF/802.11 theory. Channels, modulation, MIMO, spectrum analysis, and roaming fundamentals are CWNP's domain (CWNA/CWDP/CWNE), and this guide defers to it rather than duplicating it. It's also not a customer case tracker: the one case pattern included here has every identifying detail stripped out.

Related work — check internally first

This guide's scope overlaps with other internal Cisco efforts covering wireless troubleshooting methodology and ISE deployment/configuration guidance. Those are other engineers' internal projects and aren't detailed in this public document — check internally at Cisco before assuming this is the only resource on a given topic.

AP join failures & AAA

Catalyst 9800 (IOS-XE) · mostly documented

The misconception to rule out first

Default CAPWAP join on a 9800 has no AAA/RADIUS step at all. The sequence is purely certificate/DTLS-based:

Discovery → DTLS handshake (cert exchange) → Join → image check → Config → Run

Where AAA actually enters the picture

  • An optional, off by default feature — "Authorize APs against MAC" — checks the AP's MAC/cert against a local DB or RADIUS before join.
  • 802.1X AP-as-supplicant: a separate, often-confused mechanism that authenticates the AP's wired port to the switch, not the WLC.

The real, documented causes

CauseSignature
Certificate (MIC/SSC) expiry or invalidity%PKI-3-CERTIFICATE_INVALID_EXPIRED
Image-signing cert expiration stalls downloadField Notice FN72524 (CSCwd80290)
AP count / licensing limitse.g. 9800-CL caps at 50 APs without active Smart Licensing
Country code / regulatory mismatchSyslog: "country code (GA) and regulatory domain (-A) mismatch"
Image/version mismatchCaught at the join process's image-check step

Telling AAA-driven apart from cert/CAPWAP-driven

show ap join stats detail
show wireless stats ap discovery
show wireless stats ap join
show dtls connection          (AP-side)

show ap join stats detail returns a distinct reason string per cause — "Radius authorization of the AP has failed" reads very differently from "Certificate payload in join request contains invalid certificate."

Field takeaway inference

AAA sits in exactly one narrow, opt-in path, while cert, licensing, country, and version failures dominate the documented literature. If an AP won't join and nobody deliberately turned on AP authorization, chase the certificate or the license before you chase ISE.

CWA redirect ACL logic

documented

The core mechanism

Cisco's own CWA troubleshooting docs call the 9800 redirect ACL a punt ACL, not a security ACL:

  • permit — traffic is redirected to the portal
  • deny — traffic is exempted from redirection, passes through normally

That's the inverse of normal ACL semantics, confirmed verbatim by two independent Cisco sources.

Correct ACL shape

ip access-list extended REDIRECT
 deny ip any host <ISE-IP>
 deny ip host <ISE-IP> any
 deny udp any any eq domain
 deny udp any eq domain any
 permit tcp any any eq 80

Deny traffic to ISE PSNs and DNS; permit the rest to redirect. Skip the DNS/ISE exemptions and you get a redirect loop.

The AireOS trap

Semantics flip again on legacy AireOS: there, deny means redirect and permit means pass-through — exactly backwards from 9800. An engineer carrying habits from one platform to the other will build the ACL exactly backwards, with no obvious error on screen.

FlexConnect caveat

For locally-switched APs, the controller swaps every permit/deny when pushing the ACL to the AP. The AP-local view (show ip access list) looks inverted relative to the WLC side — expected, not corruption.

Most common real failure

ACL name mismatch between what ISE sends and what's configured on the WLC. Surfaces as:

SANET_AUTHZ_FAILURE - Redirect ACL Failure
Failed attribute name REDIRECT

ISE's default ACL name is ACL_WEBAUTH_REDIRECT (underscores) — frequently retyped with dashes, which breaks the match silently.

Verifying it

show wireless client mac-address <mac> detail   (ACL under "Server Policies")
show ip access list                               (AP CLI, FlexConnect only)
debug wireless mac <mac> monitor-time <sec>

unconfirmed — show ip access-lists (plural, WLC-side) with hit counters for this specific flow is a standard IOS-XE command that almost certainly works, but no CWA-specific doc spells out this exact use.

ISE deployment & PSN sizing

mostly documented

Sizing is session-based, not WLC-based

TierConcurrent sessionsMax PSNs
Small≤ 50k2-node pair, all personas co-located
Medium≤ 150k6, PSNs dedicated
Large> 150k50, every persona dedicated

There's no fixed PSN-per-WLC ratio. Redundancy is built per workload group — RADIUS/Guest/CWA, 802.1X, TACACS+ — not per controller.

CWA doesn't support PSN load balancing

CWA's flow is multi-stage: MAB auth → redirect → second RADIUS auth → CoA, and all of it must land on the same PSN. A load balancer that splits the second-stage auth or CoA to a different node breaks the flow intermittently — exactly the shape of a "random" failure that's hard to reproduce on demand. Cisco's own "least outstanding" method is called out as unsuitable here.

Documented alternative: a WLC-driven ordered RADIUS server list with dead-server detection tuned, not an external load balancer, unless it specifically guarantees affinity across the whole CWA flow.

Hardware & placement gotchas

  • ISE appliance hardware can't be upgraded after purchase — undersizing at buy time is permanent.
  • SNS-3895 is PAN/MnT-only; using it as a PSN gives "no additional value" per Cisco.
  • Only 2 MnT nodes are supported total — no horizontal MnT scaling.
  • PAN auto-failover needs 3+ nodes; a health-check node per site if PANs split across data centers.
  • Mismatched ISE versions between PAN and a joining node blocks registration outright.

9800-side pairing gotchas

  • Mobility MAC defaults to chassis base MAC; in HA SSO pairs, set it manually or it changes on failover and silently breaks mobility tunnels.
  • N+1 is not HA SSO — SSO is a same-chassis stateful pair, N+1 is AP site-tag failover to a separate standby. Different mechanisms, often conflated.
  • On a Catalyst-Center-managed 9800, manual CLI changes get silently overwritten on the next provisioning sync.

Intermittent failure checklist

mostly documented

For symptoms that look random, hit different users unpredictably, and resist reproduction — work this list in order.

1. RADIUS/AAA health, WLC side

  • Client exclusion when the server returns a VLAN/ACL name that doesn't exist locally.
  • EAP timeout from dot1x timeout / retry windows — often client/driver-side, not server-side.
  • debug wireless mac <addr> monitor-time <N> elevates one MAC to debug across every process.

2. ISE-side signals

  • A node out of sync with the Primary Admin node delays Application Server init (normally 15–35 min).
  • Self-signed/untrusted ISE certs show as "Alert (Level: Fatal, Description: Certificate Unknown)" in captures.
  • Check per-node CPU/latency/memory before assuming a logic bug.

3. Infrastructure signals mistaken for wireless

  • DHCP Required mismatch across foreign/anchor controllers → stale IP retained across a roam → NAK.
  • Internal 9800 DHCP defaults to an infinite lease — can quietly exhaust the pool.
  • VLAN/trunk or FlexConnect native-VLAN mismatch explains behavior that's fine at some sites, broken at others.

4. Standard correlation method

Controller:  RadioActive trace by client MAC + exact timestamp
AP:          AP-side client debug (bundle collector)
ISE:         Live Logs for the same MAC/timestamp

TAC's first ask is always the same: exact reproduction timestamp, client MAC/IP/username/session ID, and a trace captured live — continued logging overwrites debug buffers, so this can't be reconstructed after the fact.

Meraki cloud-managed (MR)

mostly documented

The architecture inverts the usual model

Meraki is event-driven RPC: the cloud initiates calls to devices for config push and telemetry — the opposite of a WLC pulling AP state. User traffic never touches the cloud; it goes direct to LAN/WAN. There's no CAPWAP and no controller to tunnel to — APs are independently intelligent.

Documented: on cloud connectivity loss, "the Meraki hardware device will continue to run with its last known configuration until cloud connectivity is restored." inference: SSIDs keep broadcasting and clients keep associating locally during an outage — only dashboard-dependent functions (new config, Live Tools, Sign-on-splash auth, see below) are affected.

Guest / web auth splash types

  • Click-through — acknowledgment only, no credentials.
  • Sign-on — via Meraki auth, RADIUS, LDAP, AD, or Google/Entra. With Sign-on + RADIUS, the client's credentials route through the Meraki Cloud Controller, which issues the Access-Request to the external server (e.g. ISE) — the cloud is in the auth path, not the local AP.

802.1X / MAB with ISE

Shared secret must match on the SSID config and the RADIUS server. Enabling "Cisco ISE Authentication" lets Meraki honor ISE's url-redirect AVPair for CWA and auto-enables CoA.

CoA/Disconnect port is platform-specific — a frequent source of "RADIUS works but CoA doesn't": the AP's UDP port must be reachable from the RADIUS server at 1700 for ISE, 3799 for other NAC vendors. CoA behavior itself changed between firmware MR25 and MR26 (full disassociation vs. in-session EAP reauth). Cloud RADIUS proxy does not support CoA at all.

The RADIUS test tool has a specific blind spot

Dashboard's built-in RADIUS test triggers an EAP-PEAP/MS-CHAPv2 exchange to confirm reachability and credentials. It fails for EAP-TLS every time, because the test has no client certificate to present — that failure means nothing about whether real EAP-TLS clients will work. Test those with an actual device.

Connectivity requirements & "unreachable" alerts

TrafficPort
DNSUDP/53

Authentication specifically has no backup-connection fallback — it requires UDP/7351 even when the general tunnel has already fallen back to HTTP/HTTPS. A site that looks "online" via the fallback path can still fail auth for this exact reason.

An "unreachable device" alert means the device was online and has stopped talking to the cloud — Dashboard's guided workflow: check the Meraki Status page, identify the upstream neighbor, packet capture, cable/LED/power check, local status page, support data bundle, reboot as last resort.

Live Tools — and the one that doesn't exist on MR

Monitor > Access Points > Tools: Ping (to client or AP), ARP table, Traceroute, Dashboard throughput test (AP↔dashboard only, not internet), blink LEDs, reboot, splash page test.

"Cable Test" is documented for MS switches, not MR access points. An engineer looking for it on an AP's tool list won't find it — easy platform-confusion mistake, not a missing feature on your specific AP.

Mixed Meraki + Catalyst 9800 fleets

Dashboard can cloud-monitor a 9800 via Cloud-Managed Hybrid Operating Mode — a reverse "Meraki Tunnel" from the 9800 to the cloud (show meraki connect on IOS-XE shows tunnel/registration state). This is onboarding/monitoring only, not native MR-equivalent management. Documented gotchas are all 9800-side: onboarding needs privilege-15 credentials with correct AAA (aaa authentication login default local / aaa authorization exec default local), and conflicts can come from VTY line limits, HTTP/NETCONF ACL conflicts, SSH port/rotary conflicts, or unsupported SSH encryption algorithms.

inference — two assumptions that don't carry over between platforms: 9800 CLI diagnostics (show wireless client, CAPWAP state) have no Meraki equivalent at all — everything is Dashboard Live Tools or API; and CoA port convention isn't shared either, since MR explicitly uses 1700/3799 while 9800/IOS-XE configures its own CoA listener.

AireOS & Mobility Express

documented

The CLI isn't just "older" — it's a different shape

AireOS is flat and non-modal: commands fully qualify their target in one line (config wlan create, config wlan interface), with no config-mode sub-shell to step into. There's also no running/startup split — config lives as XML in RAM and only reaches NVRAM via an explicit save config; logging out or resetting prompts you to save first. 9800/IOS-XE uses the modal config-mode convention most engineers already expect.

The config model itself is restructured, not just renamed

AireOS binds a WLAN directly to a VLAN interface, with AP Groups remapping that WLAN-to-VLAN binding per site. The 9800 decouples the same idea into five pieces: WLAN Profile (SSID/L2 security) + Policy Profile (VLAN/ACL/QoS) + Policy Tag (binds the two) + RF Tag + Site Tag + AP Join Profile. Changing any tag forces an AP rejoin — a side effect that surprises engineers used to AireOS's more direct model.

Debugging works completely differently

AireOS9800 / IOS-XE
debug client <mac> or debug mac addr — one global debug session, filterable by up to 10 MACsdebug platform condition feature wireless mac <mac> then debug platform condition start — radioactive tracing across every process
save configwrite memory

On AireOS, starting a new debug session kills any other active one — a second engineer debugging a different client on the same box will silently stop your trace. There's no equivalent collision on the 9800's condition-based model.

Mobility Express is not the same thing as the 9800's EWC

Classic Mobility Express is AireOS running on an AP acting as its own controller — no separate WLC hardware. Scale depends on which AP holds the Primary role: 1540/1815/1830/1850 top out at 50 APs/1000 clients; 1560/2800/3800/4800 reach 100 APs/2000 clients; the hard ceiling across the line is 100 APs/2000 clients. No Cisco table extends this to Wi-Fi 6 APs under classic ME.

Confirm you're looking at an ME deployment, not a true WLC, with show version on the AP — it reports AP Image Type: MOBILITY EXPRESS IMAGE when it's acting as its own controller.

Don't confuse this with the Catalyst 9800 Embedded Wireless Controller (EWC) — a separate, IOS-XE-based product, not AireOS ME. EWC itself is now end-of-sale (11/29/2024) with support ending 11/30/2029 and no replacement product. If you're inheriting an EWC deployment, there's no "upgrade path" to plan for — only a platform change.

Primary AP election and failover

Election priority, in order: a pinned "User Defined Master" > "Next Preferred Master" > highest-capability hardware > lowest client load > lowest MAC address. Mechanism is VRRP under the hood. No consolidated ME-vs-full-WLC feature parity table exists on Cisco.com — that gap is confirmed, not just unresearched; don't assume one platform's feature set carries over to the other without checking the specific feature.

Outdoor & mesh

documented

RAP, MAP, and the backhaul protocol

RAPs have a wired link to the controller. MAPs connect wirelessly, shipping with radio role = MAP by default (config ap role {rootAP|meshAP} to change it). MAPs find the best wireless path back to a RAP using Cisco's Adaptive Wireless Path Protocol (AWPP), forming a tree with keepalive adjacency request/response messages; VLAN-tagged traffic tunnels over that backhaul link.

The join sequence has an extra step

On a 9800, Ethernet-connected MAPs get MAC-authorized during a normal CAPWAP join — same as any indoor AP. A wirelessly-joining MAP is only authorized once it secures an AWPP link to its parent. The backhaul link has to exist before controller authorization completes, which indoor wired-join APs never have to do.

Bridge Group Name — the most common connectivity cause

Default BGN from manufacturing is NULL, which lets a MAP join before an admin assigns a network-specific BGN (max 10 characters). BGNs segment mesh networks sharing a channel. A MAP with a mismatched BGN scans 10 times for its correct parent; after 10 failed scans, it joins a non-matching BGN parent for 15 minutes before retrying its own. Cisco's documented fix order: reconfigure the farthest node first, then work back toward the RAP — reconfiguring in the wrong order can strand nodes mid-change.

Limits and timers worth knowing cold

SettingValue
Default max hop count4
Backhaul SNR thresholdsLow 12 dB, High 60 dB (DFS-heavy regions like Europe: 20 dB minimum recommended)

Why hop count matters more than it sounds like it should

Hop count isn't just added latency — it's a throughput multiplier against the whole backhaul. A client two hops out getting 5 Mbps can be consuming 40 Mbps of total backhaul capacity to deliver it. CAPWAP encapsulation itself costs up to 15% throughput on top of that.

Backhaul interference indoor troubleshooting doesn't prepare you for

  • Weather radar occupies 5600–5650 MHz (channels 124/128) and triggers DFS "quiet"/"silent" mode — a mesh link that drops specifically on those channels isn't a config problem.
  • Collocated mesh nodes need physical separation — 10 ft vertical or 100 ft horizontal — to avoid self-interference between the node's own radios.

CMX & Cisco Spaces

mostly documented

How RF data becomes a location

The controller pulls RSSI from up to 16 APs per client/tag/rogue. Probing clients send probe requests that APs forward to the controller — acknowledged probes by default, with unacknowledged probes available as an accuracy option. The controller relays all of this over NMSP: to an on-prem CMX appliance directly, or to cloud Cisco Spaces via "NMSP cloud-services" over HTTPS.

inference — Cisco Spaces reads as CMX's cloud-hosted evolution: the 9800's own config chapter is titled "Cisco Spaces," but every command inside it still says cmx. Not a direct Cisco statement, but the naming is hard to read any other way.

Accuracy add-ons — and what they actually require

FeatureRequirementAccuracy

HyperlocationDedicated AoA hardware on specific Aironet models; all APs on a floor grouped together, NTP-synced≈1m, only within the AP group's "convex hull"

Hyperlocation's 1m figure only holds inside the convex hull of the AP group that's been deployed together and NTP-synced. A test point placed outside that geometric boundary will read far less accurately, and that's expected behavior, not a defect.

HA SSO & N+1 failover

Catalyst 9800 · mostly documented, with real gaps noted

RMI and RP — the link that has to be right

The Redundancy Management Interface (RMI) and Redundancy Port (RP) must sit on the same subnet, isolated from every other interface on the box. Cisco's documented addressing recommendation is a 169.254.x.x/16 block derived from the management interface — explicitly not 10.10.10.x/24. RP round-trip time must stay under 80ms, and the HA port maps only to a 1Gbps interface (SFP takes priority over RJ-45 if both are present).

Split-brain is a named, documented condition

If RP goes down and RMI becomes unreachable at the same time, Cisco calls this a double fault: "Both controllers may become active, causing a network conflict." Role negotiation only resumes once connectivity is restored, and the controller that came up last stays active — not the one that was active before the fault. If RP alone drops during HA sync, the standby intentionally crashes when IPC communication fails, rather than risk running split.

If RP is down but RMI/gateway is still reachable: the standby becomes active, and the previous active enters rp-rec-mode (visible in the hostname) with every interface admin-down except the wireless management interface on the RMI IP.

Verification commands

What a clean SSO actually preserves

Only one CAPWAP tunnel is maintained between APs and the active controller at a time — "zero downtime for client services and no SSID outages" is the documented target, and database mirroring prevents APs from re-entering discovery.

What does not survive a switchover, documented explicitly: clients not yet in RUN state are removed, and purged entirely after 300 seconds if they haven't reconnected; NBAR flow state in local mode is lost; AVC flow context must be relearned; voice calls can't be recognized post-switchover because RTP/RTCP-based policy breaks; TCP sessions must re-establish; statistics tables aren't synchronized at all.

N+1 — a terminology gap worth stating plainly

unconfirmed terminology — the mechanism most engineers mean by "N+1" (AP failover to a separate standby controller, not a chassis pair) maps to Cisco's documented AP priming profile system: primary/secondary/tertiary controller statements pushed to APs via priming-override, mapped by name-regex filter or directly by AP MAC address. But the 9800 config guide itself never uses the term "N+1" for this mechanism — it reserves "N+1" for a separate, unrelated feature (rolling AP image upgrades across sites). Don't present the priming/N+1 equivalence as confirmed Cisco terminology; treat it as the closest documented mechanism, not a verified rename.

Documented failover logic: an AP always returns to its primary once that controller is available again. Tertiary is only used if both primary and secondary are down, and if secondary recovers while primary is still down, the AP stays on tertiary — there's no mid-outage fallback to secondary.

That last command is the one that actually answers "why didn't this AP fail over as expected" — it shows whether the AP received the priming configuration at all.

Root causes Cisco documents

  • Active and standby must run the same mode (Install or Bundle) and the same image version. Auto-upgrade exists specifically to handle "one of the redundancy port is upgraded to a newer version, and the other one is not upgraded at the same time."
  • Mismatched wireless trustpoints — same name, different keys — prevent the trustpoint from coming up after SSO forms.
  • Don't enable hyper-threading on HA VMs: "HA keepalives are lost, and a stack merge may occur."
  • VM snapshots of HA hosts are unsupported and can crash the controller.

802.1X supplicant-side failures

strong sourcing on the core thesis

The single error code that hides four different causes

Cisco's own "Cheat Sheet for Common Wireless Issues" documents AAA Error "-4" (Authentication Failed) as the WLC's single, most common error — and its documented cause list includes mismatched EAP methods between client and server, an expired client certificate, and an expired server certificate, all collapsed into the same error code. This is the concrete, Cisco-documented proof that a basic "auth failed" symptom cannot by itself distinguish a client problem from a server problem. Don't let that one error code drive an escalation decision on its own.

Machine vs. user auth ordering (EAP chaining / TEAP)

In a chained TEAP session, user identity is attempted first (ISE log 11573 Selected identity type 'User'), then machine (11574 Selected identity type 'Machine'). If user auth fails but machine auth succeeds, ISE still completes the session: 11566 TEAP inner method finished with failure for the user attempt, followed by 33517 Sent TEAP Intermediate Result TLV indicating failure, then a successful machine attempt (12528 Inner EAP-TLS authentication succeeded), and the overall session can still return 11002 Returned RADIUS Access-Accept.

Authorization is then driven by the Network Access.EapChainingResult attribute — Cisco's own documentation describes policy rules written explicitly around "machine authenticated but user not" versus "both now authenticated," confirming this differential treatment is intentional, documented design, not an edge case.

Client-side certificate trust

The WLC-side signature for a client that never responds is unambiguous: DOT1X-5-FAIL with reason (Timeout), repeated Retrying (count 3) method dot1x, ending in CO_CLIENT_DELETE_REASON_CONNECT_TIMEOUT. Cisco's own remediation text for this exact scenario reads: "Ensure wireless client trust RADIUS' certificate" — stated as a client-side action item, not a server fix.

ISE's own error 5440 corroborates from the other side: "the endpoint supplicant does not complete the EAP authentication within the configured timeout," logged as "ISE sending 'Access-Challenge' but ISE didn't receive any response." ISE did its job; the client went silent. The same abandonment pattern — "Endpoint <MAC> abandoned EAP session <session-id> and started EAP session" — recurs as a named, numbered event across independent Cisco troubleshooting documents, not an ad hoc string.

unconfirmed — no Cisco documentation found states the exact log text for "untrusted root CA," "certificate expired," or "clock skew" as distinct, separately-coded failure reasons. These are well-established real-world causes, but any specific wording attributed to them should be treated as inference, not a cited string, until confirmed against a live ISE instance or TAC case.

Multicast & broadcast over WLAN

mostly documented

IGMP snooping doesn't stop at the controller

The controller still forwards multicast to every AP over CAPWAP — snooping suppresses flooding at the AP-to-client, over-the-air hop, not the controller-to-AP hop. Only APs with an actively subscribed client send the multicast stream on a given WLAN. The controller builds unique MGIDs from the (L3 group, VLAN) pair and tracks per-AP client membership against them.

IGMPv1/MLDv1 snooping is fully supported; IGMPv2/v3 support is explicitly documented as "limited" — if the upstream switch doesn't recognize IGMPv3, hosts simply don't get traffic.

show wireless multicast
show wireless multicast group summary

show ip igmp snooping igmpv2-tracking
show wireless profile policy detail <policy-profile>    ! Multicast VLAN, Multicast Filter field

DTIM interval — a documented, hard recommendation

Cisco states this without qualification: "The only recommended DTIM values are 1 and 2; higher DTIM values will likely cause communications problems." The AP buffers broadcast/multicast frames and only releases them at the DTIM beacon — a 100ms beacon period with DTIM=1 delivers multicast 10 times per second; raising DTIM delays delivery proportionally.

inference — raising DTIM on APs serving battery-saving handhelds, badge scanners, or IoT devices delays multicast/broadcast delivery in exact proportion to beacon-interval × DTIM value. This is commonly misdiagnosed as a flaky application ("my paging app is slow," "discovery is unreliable") rather than traced back to the RF profile's DTIM setting.

QoS & voice/video over WLAN

strong on 9800 marking, thin on 9800 CAC

Metal policies, not classic AC names

9800 names its QoS tiers Platinum/Gold/Silver/Bronze rather than the raw WMM access categories: Platinum = Voice (AC_VO), Gold = Video (AC_VI), Silver = Best Effort (AC_BE, the default), Bronze = Background (AC_BK). Max DSCP per metal: Bronze 8, Silver 0, Gold 34 (AF41), Platinum 46 (EF).

Documented client-vs-WLC marking mismatch worth memorizing: the WLC maps DSCP 46 to UP 6 (Voice), while Windows maps the same DSCP 46 to UP 5 (Video). Reading a packet capture without knowing this will make a correctly-marked voice flow look misclassified when it isn't. Default behavior since 17.4 is qos-map trust-dscp-upstream.

The untrusted uplink problem, in two distinct forms

Catalyst 9000 switchports default to trusted, but two separate documented failure modes still happen in the field:

  • Wired-side remarking — an intermediate switch remarks DSCP 46 down to CS1, degrading WMM all the way to Background before the traffic ever reaches the AP.
  • Outer-header-only remarking — a switch on the AP's own uplink can only see the outer CAPWAP header, not the tunneled client traffic inside it. The inner client DSCP survives untouched, so the client-side marking looks perfectly fine — but the AP-to-WLC transport itself is deprioritized at every hop, producing jitter and loss that a client-side-only inspection will never explain.

Cisco's documented 5-step verification: capture at the source, check every intermediate switch config, capture before and after each switch plus at the WLC and the destination, simulate the path, then cross-check against the 9800 best-practice document. Current trust-boundary commands on 9000-series: trust device <type>, auto qos trust {cos|dscp}, auto qos voip {cisco-phone|cisco-softphone|trust}, verified via show auto qos and show policy-map interface. An untrusted/mismatched peer causes both CoS and DSCP to reset to 0.

Troubleshooting order — stated plainly as a synthesis

9800 ISSU upgrade methodology

documented, with explicit internal inconsistencies noted

ISSU requires a real HA pair — there's no standalone fallback

ISSU "upgrades the controller software image to a later release while the network continues to forward packets," on 9800-80/40/L/CL/M/H1/H2, install mode only. Cisco's own prerequisite check in show issu state detail validates "Standby Online" and "SSO Mode" before allowing activation. There is no documented standalone ISSU workflow anywhere in the config guide — the state machine depends on a standby to absorb traffic, so a standalone 9800 has nothing to activate first.

gap — Cisco does not document what happens if install activate issu is attempted on a standalone controller. It may fail the prerequisite check cleanly, or it may not — this is unconfirmed. For non-HA controllers, Cisco instead documents "N+1 Hitless Rolling AP Upgrade" (a separate controller pair, APs move site-tag by site-tag) as the hitless alternative. That is not ISSU and shouldn't be conflated with it.

The process flow and what to monitor

Image syncs to standby → AP predownload (no service impact) → standby reloads to the new version first while the active continues serving on the old version, forming a temporary mixed-version SSO pair → switchover (the upgraded unit becomes active) → former active reloads to match → staggered AP rejoin cycle → install commit.

show issu state detail      ! primary monitor; shows state transitions and abort-timer countdown
show redundancy              ! Active/Standby roles, "Communications = Up", peer "STANDBY HOT"
show install summary         ! I/U/C/D package flags, abort-timer status
show chassis rmi
show ap image                ! AP predownload tracking

Minor documentation inconsistency worth knowing: show redundancy appears in the separate upgrade and troubleshooting guides but not in the core ISSU config-guide chapter itself.

Rollback — default timer and real triggers

Default auto-abort timer: 360 minutes (6 hours), configurable 30–1200 via install activate issu auto-abort-timer <min>. If install commit isn't issued before expiry, the device reloads back to the previous version automatically.

install commit                      ! persist the upgrade
install abort issu                   ! manual rollback — pre-commit only
install auto-abort-timer stop        ! disables the timer; still requires a manual commit later

Documented rollback triggers: TFTP/image download failure, checksum mismatch, activating before AP predownload completes, auto-abort timer expiry, and config incompatibility causing MCL/PRC sync failures — Cisco cites specific real examples: the domain command removed in 17.6.x, snmp-server enable traps hsrp removed in 17.4.x, and invalid WPA3 AKM configuration.

Cisco's own tech note tells engineers to avoid ISSU entirely on specific builds — known defects CSCws19380 and CSCws35670 cause instability specifically in 17.15.1–17.15.4d and 17.18.1–17.18.2, and Cisco recommends a standard upgrade instead of ISSU on those exact releases. This is worth stating directly: the "safe" path is not universally safe, and Cisco documents that itself.

Confirming a supported path before you start

ISSU is supported EM-to-EM within the same train, not more than three years apart, and within any release of the same EM. Not supported: cross-major-train moves (16.x→17.x, 17.x→18.x), SM-to-EM or EM-to-SM moves, special/engineering images, LDPE↔NPE moves, downgrades, and a hard break at 27.1.1 with no ISSU path into it from any prior release. There is no live show issu capability command — Cisco publishes a static compatibility matrix instead, which has to be checked as a lookup, not queried from the CLI. show issu state detail's system check only validates runtime readiness, not version-pair eligibility — passing that check does not mean the version pair is actually supported.

AP-side behavior — even "successful" ISSU involves a rejoin

APs stay joined through most of the process, and predownload itself has no service impact — but after cutover, APs move in staggered sub-groups via ap upgrade staggered, and Cisco's documentation states directly: "when the APs rejoin, they rejoin with V2." That's a real reload and CAPWAP rejoin per AP sub-group, staggered to limit blast radius — not a seamless failover with zero rejoin, even on a fully successful run.

Cisco's own documentation is internally inconsistent on one point: one section says a mid-process SSO/HA event stops the rolling AP upgrade and requires a manual resume; another section says switchover auto-resumes it. This isn't resolved here — treat it as a known documentation gap rather than picking a side. Known defect CSCws53690 (fixed in 17.18.3) caused unwanted AP disjoin specifically during ISSU from 17.12.6a to 17.18.2, confirming AP disjoin is a real documented failure mode even on an otherwise-supported upgrade path.

Key fields: Device Detected, Device Type, Connection Check, IEEE Class (Alt-A/B), discovery mechanism ("Ieee and Cisco"), Power Allocated vs. actual consumption, and fault counters — Absent, Over Current, Short Current, Invalid Signature, and critically, Power Denied. A nonzero Power Denied counter plus an operational state of "off" is the documented signature of a port that asked for power and didn't get it.

CDP/LLDP negotiation — the silent failure mode

An AP boots at low power (under 7W) and negotiates upward via CDP. Cisco documents directly that "CDP is not supported on third-party-powered devices," which forces classification down to IEEE class alone — and 802.3at LLDP power-via-MDI is the standards-based fallback for exactly that case.

inference — no Cisco document explicitly states "a non-Cisco switch without 802.3at LLDP support will silently cap the AP at its IEEE class." But it follows directly from the documented mechanism: that switch classifies by IEEE class only, caps the AP there, and the negotiation reports success — just at a lower tier, with no error anywhere. 2-event classification (hardware class-4 detection that bypasses CDP/LLDP entirely) is Cisco's own documented mitigation for this exact gap.

Field case pattern

anonymized

No customer name, case number, or network specifics appear here — this is the generalized technical pattern only. The case-specific writeup lives in a separate, private, access-controlled repository.

Observed pattern

  1. Client completes an 802.11r FT roam successfully, reaches RUN state.
  2. About three seconds later, the controller deletes the client with an AUTH_EXPIRED-family reason — despite the client having been fully associated.
  3. About one second after that, the client retries FT and fails with Invalid PMKID — downstream of the deletion, not the cause.
  4. Client recovers via a fresh full 802.1X association.
  5. Client later stalls in CWA / WEBAUTH_REQUIRED and times out.

Why this is worth escalating

Cisco's own DevNet reference defines the AUTH_EXPIRED-family delete reason as a pre-association timeout — "client did auth phase, but never completed association." That doesn't match a client that had already reached RUN. This contradiction, not the downstream PMKID failure, is what belongs in front of TAC or Bug Search. See FT roam + CWA for the open questions it raises.
